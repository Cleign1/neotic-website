# Payload PostgreSQL upgrade: 3.24.0 to 3.90.2

The old lockfile resolves Payload and its adapters/plugins to **3.24.0**. Production PostgreSQL does not run development schema push. Deploying the new packages without this migration breaks user queries and login.

`20261003_134406_payload_3_90_2` was generated by Payload's PostgreSQL migration generator from the **complete application configuration**, including Lexical, Payload Cloud and S3, at both versions. It adds:

- `users_sessions` with its parent foreign key and indexes;
- nullable `users.reset_password_requested_at`;
- `payload_kv` with its unique key index;
- nullable `media._objectkey`, introduced by the S3 plugin.

The migration itself does not rewrite existing users, password hashes/salts, roles or content. Sessions remain enabled. Existing passwords still work; Payload 3.90.2 then automatically upgrades legacy hashes to its new `pbkdf2-sha256-v1` format on successful login. Users should sign in again to obtain a session-backed token; preservation of old JWTs is not promised.

## Required before deployment

1. Install the reviewed lockfile with `pnpm install --frozen-lockfile`. Keep the old application release available for recovery.
2. Back up the database and verify restoration into an isolated staging database. Preserve the existing `PAYLOAD_SECRET` and storage configuration; do not generate a new production secret for this upgrade.
3. Compare the restored schema with `tests/fixtures/payload-3.24.0/schema.json` / `populated.sql`. This is an **upgrade of an existing complete 3.24.0 schema**, not a fresh-database initializer. Verify `users` and `media` exist, the four additions above are absent, and any previous migration history has been reviewed. If staging already ran 3.90.2 development schema push, restore the pre-upgrade backup instead of forcing this migration through.
4. Run the migration on that staging restore with the deployment configuration and privileges to create tables/indexes and alter tables:

   ```sh
   NODE_ENV=production pnpm migrate:status
   NODE_ENV=production pnpm migrate
   NODE_ENV=production pnpm migrate:status
   ```

   These commands use `DATABASE_URI`, `PAYLOAD_SECRET` and the normal S3 configuration. `payload.config.ts` pins the migration directory to the repository's `migrations/`. Payload's CLI disables schema push while migrating. The runner records the migration transactionally; rerunning `pnpm migrate` skips it once applied. The DDL intentionally does not use `IF NOT EXISTS`: untracked schema drift must fail rather than be silently accepted.

   If Payload warns about a development migration (`payload_migrations.batch = -1`), **stop**. After a verified baseline restore/schema comparison, a DBA may remove only that development marker to adopt migration tracking. Do not delete real migration history, accept a data-loss prompt blindly, or use `migrate:fresh`, `migrate:reset` or `migrate:refresh` on populated databases.
5. On staging, verify existing admin and Editor sign-in, authenticated requests, unchanged roles/content, and media retrieval. Run the isolated regression below as well. Build the application with the upgraded staging schema available.
6. Only after backup and staging validation, schedule a controlled deployment: stop application writers, have an authorized operator run the same migration once against the intended production database, verify its recorded status and smoke checks, then start the upgraded application. Do not rely on a Vercel build/start to apply DDL automatically.

This change does not connect to production or automate deployment.

## Recovery

Prefer restoring the verified pre-upgrade backup and old release together. **Schema DOWN alone is not a safe rollback to 3.24.0 after successful logins:** the new runtime has lazily rehashed those users' passwords into a format the baseline runtime does not recognize. The generated `down` migration removes the four additions, **including all new session records, KV values and S3 object-key metadata**. It does not rewrite persisted user/content rows but is not lossless after the new application has served traffic. Do not run it routinely on a live database. Payload runs UP/DOWN within transactions; the regression exercises a DOWN/UP cycle only on disposable test data, staying on the 3.90.2 runtime.

For future changes, use `pnpm exec payload migrate:create <name>` with the checked-in latest migration snapshot, inspect the generated SQL, and validate it against a restored populated staging database.

## Isolated regression

Use a dedicated disposable PostgreSQL 17 database named `neotic_test`, published on loopback only. Supply generated test credentials, never the application `DATABASE_URI`:

```sh
USERS_ACCESS_TEST_DATABASE_URI='postgres://<test-user>:<test-password>@127.0.0.1:<test-port>/neotic_test' pnpm test:integration
```

`test:integration` fails if the variable is absent; both tests reject non-loopback hosts and other database names. Each test owns a random schema and registers teardown before connecting. The upgrade test restores the complete real 3.24.0 schema with synthetic users/content, reproduces the missing-session-table failure, runs the supported migration runner, checks unchanged IDs/password hashes/salts/roles/content immediately after migration, verifies both existing user logins and token authentication plus Payload's lazy password rehash, exercises KV storage and S3's new column, reruns UP to verify its ledger, and tests DOWN/UP. `pnpm test` may skip integration tests without a test database; the dedicated command is required for release verification.
